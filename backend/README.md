# JEE Physics Adaptive Learning — Backend

FastAPI + SQLite backend with a multi-level Elo rating engine, adaptive question
selection, and two LLM-driven features (failure-testing diagnostics, Risk Arena
coach report) built on Groq.

## Setup

```powershell
cd backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

## Run

From the `backend/` directory:

```powershell
uvicorn app.main:app --reload --port 8001
```

On first startup the app creates `data/app.db` (project root `data/` folder) and
seeds the `questions` table from `data/questions_master.json` (run
`python scripts/consolidate_questions.py` first if that file doesn't exist).

Verify: http://localhost:8001/health → `{"status": "ok", "questions_loaded": 60}`

Interactive API docs: http://localhost:8001/docs

To reset all player/session state, stop the server, delete `data/app.db`, and
restart — it reseeds automatically. Deleting `data/app.db` does **not** touch
`data/questions_master.json`.

## Environment

`backend/.env` (gitignored) holds:

```
GROQ_API_KEYS=key1,key2,key3,...
GROQ_MODEL=llama-3.3-70b-versatile
```

`llm.py` reads a comma-separated list so it can rotate across multiple free-tier
keys if one gets rate-limited. A single `GROQ_API_KEY` also works.

## File-by-file

### `app/main.py`

The FastAPI application entrypoint. Responsibilities:

- Builds the `FastAPI` app with a `lifespan` context manager that runs once at
  startup: `Base.metadata.create_all(bind=engine)` creates all tables (SQLite
  file at `data/app.db`) if they don't exist, then `seed_questions_if_empty()`
  loads `data/questions_master.json` into the `questions` table **only if the
  table is currently empty** — safe to restart the server repeatedly without
  duplicating or re-seeding data.
- `seed_questions_if_empty()` maps each JSON question's `theta_q_seed` field to
  the live `theta_q` column — this is the one-time initialization of a
  question's difficulty rating; after that, `theta_q` is only ever updated by
  `elo.apply_attempt_result()`.
- CORS middleware uses `allow_origin_regex=r"http://(localhost|127\.0\.0\.1):\d+"`
  rather than a fixed origin list, because Vite's dev server picks whatever
  port is free (5173, 5174, ...) — hardcoding one origin breaks the frontend
  the moment that port is taken by something else.
- Registers all four routers (`players`, `quiz`, `risk_arena`, `reports`) with
  no path prefix conflicts (each router owns its own prefix internally, except
  `quiz.py` which defines two prefixes — see below).
- `GET /health` — returns `{"status": "ok", "questions_loaded": <count>}` for a
  fast liveness/seed-check.

### `app/database.py`

SQLAlchemy engine/session wiring. Nothing else in the app should import
`sqlite3` or construct its own engine.

- `DB_PATH` resolves to `<project root>/data/app.db` by default, but honors an
  `ELO_DB_PATH` environment variable override — every test script in
  `scripts/` sets this to a scratch temp-file path so tests never touch the
  real database.
- `engine` is created with `connect_args={"check_same_thread": False}`, which
  SQLite requires when a connection may be used from a different thread than
  it was created in (FastAPI's request-handling under Uvicorn can do this).
- `get_db()` is a FastAPI dependency (`Depends(get_db)` in every router
  endpoint) that yields a `SessionLocal()` instance and guarantees `db.close()`
  runs even if the request handler raises.

### `app/models.py`

All seven SQLAlchemy ORM table definitions, matching the schema from the
project spec exactly:

- **`Question`** — `question_id` is the primary key (string, e.g.
  `physics_mechanics_01`). `theta_q` is the **live** difficulty rating (seeded
  from `theta_q_seed` at load time, then mutated by every attempt). `options`,
  `marking_scheme`, `solution_steps`, `formulas_used` are all stored as JSON
  columns — SQLite has no native array/object type, so SQLAlchemy serializes
  Python lists/dicts to a JSON text column transparently.
- **`Player`** — `theta_overall` / `rd_overall` default to 1200 / 350 (the
  starting Elo rating and maximum rating deviation). `player_id` is a UUID
  string generated by the shared `_uuid()` helper.
- **`PlayerTopicRating`** — one row per `(player_id, topic)` pair, created
  lazily (see `elo.py`) the first time a player attempts a question in that
  topic. `attempts_count` drives the shrinkage weighting in
  `get_effective_rating()`.
- **`PlayerModeRating`** — same lazy-row pattern, keyed by `(player_id, mode)`
  instead of topic. Modes are `"practice_quiz"` and `"risk_arena"` —
  `"placement"` deliberately never gets a row here (see `elo.py`).
- **`Session`** — one row per quiz/placement/arena run. `config` is a JSON
  column holding whatever per-session parameters that mode needs (placement:
  `num_questions`; practice quiz: `topic_filter` + `num_questions`; risk arena:
  `num_rounds`) — added in Phase 2 specifically so the practice quiz could
  remember its topic filter and question count between `/start` and `/next`
  calls without threading extra query params through every endpoint.
- **`AttemptLog`** — the single append-only table every mode writes to. Notable
  columns: `theta_p_before` / `theta_q_before` are the ratings **as they stood
  immediately before this attempt** (captured by `elo.py` before it mutates
  anything) — this is what makes the Risk Arena coach report's retrospective
  "what was the win probability at the time" math possible. `hand_raised` is
  `None` for placement/practice (only meaningful in risk_arena). `attempted`
  is `True` for placement/practice always (no skip option there) and
  `False`/`True` in risk_arena depending on whether the hand was raised.
- **`FailureDiagnostic`** — one row per failure-test session on one wrong
  question. `generated_probe_questions` and `player_responses` are JSON arrays
  built up incrementally across the probe/respond request cycle.
  `identified_gap_step` / `identified_gap_description` stay `None` until the
  final interpretation LLM call completes.

### `app/elo.py`

**The single source of truth for all rating math.** No other file in the
backend computes an Elo update inline — every router imports functions from
here. This constraint is what keeps the three rating tracks (overall, topic,
mode) and the question's own difficulty rating mathematically consistent with
each other.

- `expected_probability(theta_p, theta_q)` — standard logistic Elo expectation,
  `1 / (1 + 10^((theta_q - theta_p)/400))`. Returns 0.5 at equal ratings, ~0.909
  at a +400 advantage.
- `update_rating(theta, rd, opponent_theta, actual_outcome, base_k=40)` — one
  rating's update after one outcome. The effective K-factor is
  `base_k * (rd / 350)`, so a player with maximum uncertainty (rd=350) gets the
  full ±40-scaled swing, while a confident player (low rd) gets much smaller
  moves. `rd` itself shrinks by 5% every call (`rd * 0.95`), floored at 50 so it
  never fully collapses (a fully-confident rating would stop updating at all).
- `get_effective_rating(specific_theta, specific_rd, parent_theta,
  attempts_count)` — the shrinkage/blending function. Below 15 attempts in a
  specific bucket (a topic, or a mode), the returned rating is a linear blend
  toward the parent (overall) rating; at 15+ attempts it's 100% the specific
  rating. This is why a brand-new topic or mode doesn't show a wildly noisy
  number after 1-2 questions — it's why `get_effective_rating` also backs the
  question selector's targeting and every "effective rating" shown in the
  frontend (topic cards, mode ratings, risk arena targeting).
- `QUESTION_PSEUDO_RD = 175.0` — questions have no natural "rd" of their own in
  the spec, but the consistency rule requires the question's `theta_q` mirror
  update to also go through `update_rating()` (never inline math). A fixed
  pseudo-RD of 175 gives questions an effective K of 20 — half a fresh
  player's K of 40 — which is a deliberate design choice: a single wrong/right
  answer from one player should move a question's global difficulty rating
  more slowly than it moves that player's own rating, since the question faces
  many players over time.
- `_get_or_create_topic_rating` / `_get_or_create_mode_rating` — the lazy-row
  helpers referenced above. Both create the row with the spec's exact seed
  values (1200/350/0 attempts) if it doesn't exist yet, then return it for the
  caller to mutate.
- `apply_attempt_result(player_id, question_id, mode, correct, db_session)` —
  **the one function every router calls to record an attempt.** In order,
  atomically (single try/except wrapping a `db_session.commit()`, with
  `db_session.rollback()` on any exception):
  1. Updates `player.theta_overall` / `rd_overall` against the question's
     `theta_q` — always, regardless of mode.
  2. Updates (lazily creating if needed) the `player_topic_ratings` row for the
     question's `topic`.
  3. Updates (lazily creating if needed) the `player_mode_ratings` row for the
     session's `mode` — **except when `mode == "placement"`**, per the spec:
     placement calibrates the overall/topic ratings but isn't itself a
     trackable skill.
  4. Updates `question.theta_q` via the mirror-image outcome (`1 - outcome`
     against the player's *before* rating) — the question "wins" when the
     player is wrong, "loses" when the player is right.

  All four updates read from the same before-attempt snapshot
  (`theta_p_before`, `theta_q_before`) captured at the top of the function, so
  there's no risk of update #2 accidentally using a `theta_q` already mutated
  by update #4. Returns a dict of before/after values and deltas — routers use
  this to log `attempt_log` rows and to show the frontend exactly how much
  each rating moved.

### `app/question_selector.py`

The single adaptive question-picking function, shared by placement, practice
quiz, and risk arena — no mode re-implements its own selection logic.

- `_rating_source(db_session, player, mode, topic_filter)` — decides which
  rating to target: the player's `risk_arena` mode rating (effective, blended)
  if `mode == "risk_arena"`; the topic rating (effective, blended) if a
  `topic_filter` is given; otherwise the raw overall rating. This is why
  placement (no topic filter) always targets overall, while a topic-filtered
  practice quiz targets that topic's calibrated difficulty.
- `select_next_question(player_id, mode, topic_filter, exclude_ids,
  db_session)` — the full algorithm:
  1. Resolve `(theta, rd)` via `_rating_source`.
  2. Query candidate questions matching `topic_filter` (or all topics) and not
     in `exclude_ids` (already-served questions in this session).
  3. `target_band = max(rd, 150)` — never let the search band collapse below
     150 points even for a very confident (low-rd) player, so there's always
     some variety instead of the same 1-2 questions repeating.
  4. Score every candidate by `abs(question.theta_q - theta)`, take the 6
     nearest, and pick one via `_weighted_random_choice` with weight
     `1/(1+distance)` — closer questions are more likely but it's not
     deterministic, so two players at the same rating don't always see
     identical question sequences.
  5. If no candidates fall within `target_band`, retry once at `1.5x` the
     band. If still empty (pool exhausted or topic too narrow), fall back to a
     fully random choice from all remaining candidates rather than erroring.
  6. Returns `None` only when the candidate pool itself is empty (no more
     unexcluded questions at all) — callers (`quiz.py`, `risk_arena.py`)
     interpret this as "end the session early."

### `app/bots.py`

Risk Arena's three NPC opponents — deliberately minimal, since bots are
supporting cast, not the graded feature.

- `ARCHETYPES` — a dict of the three fixed personalities from the spec:
  `rusher` (overconfident, low risk_multiplier, fast reactions), `skipper`
  (underconfident, high risk_multiplier, slow reactions), `calibrated`
  (accurate self-assessment, multiplier 1.0). `confidence_bias` is added
  directly to the bot's true theta before computing its perceived win
  probability — this is what makes rushers over-attempt and skippers
  under-attempt relative to their actual skill.
- `BOT_NAMES` — cosmetic display names (`Blaze`, `Turtle`, `Sage`) so the
  leaderboard reads better than raw archetype strings.
- `bot_decide(bot_theta, archetype, theta_q, marking_scheme)` — computes the
  bot's *perceived* win probability (`bot_theta + confidence_bias` vs.
  `theta_q`, via `elo.expected_probability`), the breakeven probability implied
  by the marking scheme (`penalty / (reward + penalty)`, with penalty
  converted to a positive magnitude first), and attempts whenever perceived
  probability exceeds `breakeven * risk_multiplier`. A reaction time is drawn
  uniformly from the archetype's `reaction_range` — cosmetic only, doesn't
  affect scoring.
- `bot_answer_correct(bot_true_theta, theta_q)` — separate from the decision:
  once a bot decides to attempt, whether it's actually *right* is a coin flip
  weighted by its **true** theta (no confidence bias) against the question's
  difficulty. This split is intentional — a rusher can decide to attempt out
  of overconfidence and still get it wrong at the rate its real skill implies.

### `app/llm.py`

The single Groq wrapper — every LLM-touching feature (failure-test probe
generation, failure-test diagnosis, risk-arena coach report) calls through
`call_llm_json`. Nothing else in the backend imports the `groq` package
directly.

- Reads `GROQ_API_KEYS` (comma-separated) from `backend/.env` via
  `python-dotenv`, falling back to a single `GROQ_API_KEY` if that's what's
  set. `GROQ_MODEL` defaults to `llama-3.3-70b-versatile`.
- `_parse_json(text)` — tolerant JSON parser: strips a
  ```` ```json ... ``` ```` fence if the model wrapped its output in one
  despite instructions, and if that still doesn't parse, regex-extracts the
  first `{...}` block and tries again. Handles the two most common ways a
  small/fast model deviates from "return ONLY valid JSON."
- `call_llm_json(system_prompt, user_message, max_retries=1, temperature=0.4)`
  — the actual call. Uses Groq's `response_format={"type": "json_object"}` to
  bias the model toward valid JSON in the first place, then still runs it
  through `_parse_json`. On a JSON parse failure, retries once with the *same*
  key (transient model flakiness). On any other exception (rate limit, auth,
  network), rotates `_key_idx` to the next key in the list and retries — this
  is the key-rotation mechanism that lets the app survive one key hitting its
  free-tier rate limit mid-demo. Returns `None` if every attempt across every
  retry fails, which is the signal every caller uses to fall back to a
  non-LLM path (never crashes a route).

### `app/routers/players.py`

- `POST /players/create` — `{name}` → creates a `Player` row at the spec's
  default rating (1200/350), returns the player id and starting ratings. No
  password, no auth — this is the entire "account system" for the demo.
- `GET /players/{player_id}` — returns overall rating plus, for **every**
  topic that exists in the `questions` table (not just ones the player has
  touched), an effective rating computed via `get_effective_rating` — topics
  with zero attempts correctly show the player's overall rating (0% weight on
  the nonexistent specific rating) rather than a missing/null entry. Also
  returns whatever mode ratings exist (`practice_quiz`, `risk_arena` — never
  `placement`). This endpoint backs the frontend's home-screen rating grid.

### `app/routers/quiz.py`

Placement and practice quiz share nearly all their logic — this file
implements both, plus their common helpers, in one place rather than
duplicating the flow twice.

- `router = APIRouter(tags=["quiz"])` has **no path prefix** — routes are
  registered with explicit full paths (`/placement/...` and `/quiz/...`)
  because the two flows live under different URL roots but share one file.
- `SubmitBody` / `QuizStartBody` — Pydantic request schemas.
- `_get_session(db, session_id, expected_mode)` — looks up a session and
  404s if it doesn't exist *or* if its `mode` doesn't match what the calling
  endpoint expects (e.g. calling `/quiz/{id}/next` with a placement session id
  correctly 404s rather than silently operating on the wrong session type).
- `_session_attempts` — all `AttemptLog` rows for a session, ordered by
  `round_num`. Used both to count progress and to build the exclude-list for
  question selection.
- `_next_question(db, session, num_questions)` — shared by both
  `/placement/{id}/next` and `/quiz/{id}/next`. Marks the session `ended_at`
  and returns `{"complete": true}` once `num_questions` have been served, or
  earlier if `select_next_question` returns `None` (pool exhausted). Otherwise
  calls the selector, **shuffles the returned question's options** (every
  question in `questions_master.json` happens to list the correct answer
  first — a byproduct of how the raw batches were LLM-generated — so this
  shuffle is what prevents "always pick option A" from being a winning
  strategy; correctness checking is by string match so display order doesn't
  matter), and returns question text/options/topic plus round/total counters.
  Never includes `correct_answer` in the response.
- `_submit(db, session, body, scored)` — shared by both submit endpoints. Looks
  up the question, 404s if it doesn't exist, and 409s if this
  `(session_id, question_id)` pair was already answered (prevents double
  submission / replay). Computes correctness by exact string match, then calls
  `elo.apply_attempt_result(mode=session.mode, ...)` — this is the *only*
  place ratings are touched in this file. `scored` controls whether
  `points_delta` uses the question's `marking_scheme` (practice quiz) or is
  forced to `0.0` (placement — unscored calibration per spec, though the
  Elo update still happens). Logs one `AttemptLog` row with the before-ratings
  captured from the `apply_attempt_result` return value, then returns the
  correctness reveal, the correct answer, and the rating deltas the frontend
  animates.
- **Placement endpoints**: `POST /placement/{player_id}/start` (creates a
  session with `config={"num_questions": 8}`), `GET
  /placement/{session_id}/next`, `POST /placement/{session_id}/submit` (always
  `scored=False`), `GET /placement/{session_id}/summary` — computes, for every
  topic, the effective rating exactly like `GET /players/{id}` does, plus
  overall theta/rd and a correct/total count. This is what backs the "your
  rating is X" reveal screen.
- **Practice quiz endpoints**: `POST /quiz/{player_id}/start` (`{topic_filter,
  num_questions}`, validates `topic_filter` against the actual distinct topics
  in the DB and 422s on an unknown one), `GET /quiz/{session_id}/next`, `POST
  /quiz/{session_id}/submit` (`scored=True`), `GET /quiz/{session_id}/summary`
  — total score (sum of `points_delta`), accuracy %, average reaction time,
  a per-topic accuracy breakdown, and the `{question_id, was_correct}` list
  that Phase 3's report/failure-testing endpoints consume.

### `app/routers/risk_arena.py`

The hand-raise mini-game. This is the one router with meaningful **in-memory**
state (`ARENA_STATE`, a module-level dict keyed by `session_id`) alongside the
database — bot scores/theta don't need to survive a server restart per the
spec, so they're never persisted. `_get_arena` returns a clear `410 Gone` if a
session's in-memory state is missing (e.g. after a server restart), rather
than a confusing crash or silent wrong behavior.

- `COACH_SYSTEM_PROMPT` — the one LLM prompt used by the coach report,
  described inline in the router since it's tightly coupled to the JSON shape
  built just above the `call_llm_json` call.
- `_get_arena(session_id)` — the state lookup + 410 guard described above.
- `_leaderboard(state, player_name)` — builds and sorts the 4-row
  player+3-bots leaderboard by score descending; also carries each row's
  `last_action` (`"correct"` / `"wrong"` / `"skipped"` / `None` before the
  first round) for the frontend's per-row status tag.
- `POST /risk_arena/{player_id}/start` — creates the `Session` row
  (`mode="risk_arena"`), then **pre-selects all `num_rounds` questions
  up-front** (not one at a time as rounds are played) by repeatedly calling
  `select_next_question(mode="risk_arena", topic_filter=None, ...)`, which
  targets the player's *effective* risk_arena mode rating — for a brand new
  player with zero risk_arena attempts, `get_effective_rating` correctly falls
  back to 100% their overall rating. If `first_session` is true, bots are the
  fixed `[calibrated, rusher, skipper]` lineup from the spec; otherwise three
  random archetypes are sampled (archetype variety for repeat play, not
  currently exposed in the frontend UI but supported by the API). Initializes
  `ARENA_STATE[session_id]` with each bot's `theta` seeded at 1200 and
  `score` at 0.
- `GET /risk_arena/{session_id}/round/{n}` — returns the pre-selected
  question for round `n` (1-indexed), options shuffled (same reasoning as
  `quiz.py`), plus `theta_q` and `marking_scheme` so the frontend can display
  difficulty and stakes before the player decides. Never leaks the answer.
- `POST /risk_arena/{session_id}/round/{n}/submit` — the core round
  resolution, in this order:
  1. 409s if this round number was already submitted (`state["submitted_rounds"]`
     is a set, checked before any mutation).
  2. Runs `bot_decide` + (if attempting) `bot_answer_correct` for each of the 3
     bots, purely in-memory — updates each bot's `score` and `last_action`.
  3. Resolves the player: if `hand_raised`, requires `selected_answer` (422 if
     missing), checks correctness, calls
     `elo.apply_attempt_result(mode="risk_arena", ...)` (the only DB rating
     mutation in this endpoint), and accumulates `points_delta` into
     `state["player_score"]`. If not raised, **no Elo update happens** — but
     the round is still logged via `AttemptLog` with `theta_p_before` /
     `theta_q_before` captured from the player's/question's *current* values
     (not stale) — this is what makes the coach report's retrospective
     "what were the odds when you skipped this" math possible. This
     unconditional logging (attempted or not) is deliberate per the spec's
     "risk-log completeness" requirement.
  4. Marks the round submitted, and if it was the last round, sets
     `session.ended_at`.
  5. Recomputes the player's *effective* risk_arena rating post-update (via
     `get_effective_rating`, reading the just-updated `PlayerModeRating` row)
     to return in the response — this is the number the frontend animates.
  6. Returns the answer reveal, the player's outcome, every bot's outcome, the
     freshly-sorted leaderboard, and `session_complete` (true on the final
     round) so the frontend knows whether "Next round" should instead route to
     the coach report.
- `GET /risk_arena/{session_id}/coach_report` — the retrospective analysis,
  computed entirely from `AttemptLog` rows (works even after a server restart
  wiped `ARENA_STATE`, except the final leaderboard section which needs the
  in-memory bot scores and is `None` if that state is gone). For every logged
  round: recomputes `p = expected_probability(theta_p_before, theta_q_before)`
  (the win probability *at the time*, using the captured before-ratings, not
  current ones), the marking-scheme-implied `breakeven` probability, and
  `optimal_ev = max(0, p*reward - (1-p)*penalty)` — the expected value of
  attempting under perfect calibration (floored at 0, since a perfectly
  calibrated player would just skip when EV is negative). A round is
  `divergent` if the player's actual decision (attempt/skip) disagreed with
  what `p > breakeven` implies they should have done. `biggest_divergence` is
  the divergent round with the largest `|optimal_ev - points_delta|` gap — the
  single costliest bad call, surfaced as a specific callout rather than a
  generic stat. `gap = optimal_score - actual_score` is the headline number.
  One `call_llm_json` call turns these numbers into 3 coaching points; if that
  fails twice, a hardcoded fallback still references the actual gap/divergence
  counts (never generic filler) so the report never looks broken even without
  a working LLM call.

### `app/routers/reports.py`

The detailed report and the two-call failure-testing diagnostic flow — Phase
3's headline feature. Works for **any** session mode (placement or practice
quiz) since the underlying data (`AttemptLog`, wrong answers) isn't
mode-specific; the frontend currently surfaces it on both summary screens.

- `MAX_FAILURE_TESTS_PER_SESSION = 3` — the hard cap from the spec, enforced
  server-side (not just hidden in the UI) so the endpoint itself 409s past the
  limit even if called directly.
- `PROBE_SYSTEM_PROMPT` / `DIAGNOSIS_SYSTEM_PROMPT` — the two prompts, verbatim
  from the spec, each demanding strict JSON with a specific shape.
- `_get_session` — 404 guard, shared.
- `_wrong_attempts(db, session_id)` — all `AttemptLog` rows in a session where
  `attempted=True and correct=False` — the pool of questions eligible for
  failure-testing.
- `_session_diagnostics(db, session_id)` — every `FailureDiagnostic` row
  belonging to attempts in this session, used both to check the 3-per-session
  cap and to report each wrong answer's diagnostic status.
- `GET /reports/{session_id}` — the detailed report. Builds per-topic
  accuracy **and average `theta_q_before` faced** (the "you got 60% but the
  questions were hard" context from the spec) by summing `theta_q_before`
  across attempts in each topic. Builds the `wrong_answers` list with each
  entry's `diagnostic_status` — `"none"` (never started), `"in_progress"`
  (probes generated, not all responded to yet), or `"diagnosed"` (complete) —
  computed by checking whether a `FailureDiagnostic` row exists for that
  attempt and whether it has an `identified_gap_description` yet. Returns
  `failure_tests_used` / `failure_tests_max` so the frontend can grey out the
  "Diagnose" button once the session's budget is spent.
- `POST /reports/{session_id}/failure_test/{question_id}` — starts a
  diagnostic. 404s if there's no wrong attempt for that question in this
  session (can't failure-test a question you got right, or one from a
  different session). **Idempotent**: if a `FailureDiagnostic` already exists
  for this attempt, returns its stored probes rather than calling the LLM
  again or erroring — lets the frontend safely re-navigate to an in-progress
  diagnosis. Otherwise checks the 3-per-session cap (409 if exceeded), builds
  a JSON user message from the question text, options, the student's actual
  wrong answer, the correct answer, and the question's pre-authored
  `solution_steps` (the LLM never invents the solution path — grounding is
  structural, not just a prompt instruction), and calls `call_llm_json` with
  `PROBE_SYSTEM_PROMPT`. Validates the response shape defensively (must be a
  non-empty list of dicts each containing `probe_question`) before trusting
  it; on any failure (LLM returned `None`, or a malformed/empty `probes`
  list), returns `{"fallback": true, "solution_steps": ...}` **without**
  creating a `FailureDiagnostic` row — so a later retry of this same endpoint
  can still succeed and go interactive instead of being stuck in fallback
  forever. On success, stores the cleaned+sorted probes and an empty
  `player_responses` list.
- `POST /reports/{session_id}/failure_test/{question_id}/respond` — accepts
  one `{step_order, player_response}` at a time (the frontend's interactive
  one-probe-at-a-time UX). 404s if no diagnostic was started; 409s if this
  question's diagnosis is already complete (`identified_gap_description` is
  set). Appends the response (reassigning `diag.player_responses = responses`
  rather than mutating in place, since SQLAlchemy's JSON column change
  tracking needs a new object to detect the update). If not all probes have
  been answered yet, returns the running `{answered, total}` count so the
  frontend can advance to the next probe. Once the last response arrives,
  makes the **single** interpretation `call_llm_json` with
  `DIAGNOSIS_SYSTEM_PROMPT`, passing the question, the ground-truth solution
  steps, the generated probes, and all collected responses. Validates and
  coerces the result (`gap_step_order` safely cast to `int` or `None`,
  `confidence` forced to one of the three valid enum values); on total LLM
  failure, substitutes a generic-but-honest fallback diagnosis rather than
  erroring the request. Persists `identified_gap_step` /
  `identified_gap_description` and returns the diagnosis plus the full
  `solution_steps` array so the frontend's reveal screen can render the
  broken step highlighted against the complete correct solution.

## Test scripts (`../scripts/`)

Not part of the running app — used during development to verify each phase
before building the next one on top of it. All of them redirect
`ELO_DB_PATH` to a scratch temp file before importing anything from `app/`, so
running them never touches your real `data/app.db`.

- **`test_elo.py`** — unit-level checks of every function in `elo.py` in
  isolation (expected probability at various rating gaps, K-scaling by RD, RD
  floor, shrinkage blending at 0/5/15+ attempts) plus one full
  `apply_attempt_result` call verified against hand-computed expected deltas,
  a placement-mode call verified to skip the mode-rating row, and an
  unknown-player call verified to raise and roll back cleanly.
- **`test_phase2.py`** — end-to-end via FastAPI's `TestClient` (no real HTTP
  server needed): creates a player, runs a full 8-question placement quiz,
  checks the answer-leak guard and duplicate-submit guard, runs a
  topic-filtered scored practice quiz, and checks the resulting summary
  numbers and rating movement.
- **`test_phase3.py`** — same `TestClient` approach, but makes **real Groq API
  calls**. Runs a 4-question quiz with 2 deliberately-wrong answers, checks
  the detailed report's math, then drives the full failure-testing flow
  (probe generation → idempotent re-fetch → answering probes with a
  deliberately-confused final answer → checking the diagnosis correctly
  identifies the planted misunderstanding), plus the 404 guards for
  unattempted/correctly-answered questions.
- **`test_phase4.py`** — unit tests for `bot_decide` under different rating
  gaps, then an end-to-end 6-round arena session mixing correct/wrong/skip
  player decisions, checking scoring, the skip-doesn't-update-elo rule, the
  duplicate-submit and out-of-range guards, and a real Groq call to the coach
  report (checked against hand-computed `p`/`breakeven`/`optimal_ev` values).

Run any of them with `python scripts/<name>.py` from the project root.
